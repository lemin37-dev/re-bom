## 4. 상태값 정리

### 4.1 두 로그의 `status`는 뜻이 다릅니다

| 로그 | 한 행 | `status`가 답하는 질문 |
|---|---|---|
| 처리 로그 `gold_inference_log` | 대상 1개 × 작업 × 버전 × 입력 | **이 사진(글)을 처리했나? 다시 해야 하나?** |
| 요청 로그 `gold_model_request_log` | 모델 호출 1번 | **이 호출이 성공했나? 얼마 들었나?** |
| canary `gold_embedding_canary` | 점검 1번 | 모델이 바뀌었나? (`passed`) |

같은 사진은 처리 로그에서 **항상 한 행**입니다. 다시 처리하면 새 행이 아니라 **그 행이 바뀝니다.** 요청 로그는 호출마다 행이 **추가**됩니다.

### 4.2 사진 임베딩의 처리 상태 [코드]

| `status` | 언제 남나 | 모델 호출 | 벡터 | 다음 실행 | prod 건수 |
|---|---|---|---|---|---|
| `OK` | 벡터를 만듦 | 했음 | 있음 | 보내지 않음 | 37,311 |
| `BLANK` | 거의 한 색인 빈 사진 (표준편차 4.0 미만) | 안 함 | 없음 | **보내지 않음** | 3 |
| `BAD_IMAGE` | 파일은 받았지만 이미지로 열리지 않음 | 안 함 | 없음 | **보내지 않음** | 0 |
| `READ_ERROR` | S3에서 파일을 못 읽음 (없음·권한·네트워크) | 안 함 | 없음 | **다시 시도** | 0 |
| `SHA_MISMATCH` | 받은 파일의 sha256이 기록과 다름 | 안 함 | 없음 | **다시 시도** | 0 |
| `API_ERROR` (#79, 병합 전) | 모델 호출이 재시도까지 끝내 실패 | **했음** | 없음 | **다시 시도** | - |

### 4.3 상태별로 남는 기록 [코드]

| `status` | `attempts` | `detail` | `last_error` |
|---|---|---|---|
| `OK` | 1 | `{"request_id": …, "batch_size": 1}` (11/24 이전 이관 행은 비어 있음) | 비움 |
| `BLANK` | 1 | `{"gray_std": 0.0, "blank_std": 4.0}` | 비움 |
| `BAD_IMAGE` | 1 | `{"s3_key": …}` | `bad_image:<오류 종류>` |
| `READ_ERROR` | **연속 실패 횟수** | `{"s3_key": …, "error": "NoSuchKey"}` | `read_error:<오류 코드>` |
| `SHA_MISMATCH` | 1 | `{"s3_key": …}` | `sha_mismatch` |
| `API_ERROR` | **연속 실패 횟수** | `{"s3_key": …, "error": "429"}` | `api_error:<코드>` |

- 공통 칸: `subject_type = photo`, `subject_key = input_hash = sha256`, `task = image_embedding`, `version = gemini-embedding-2:768/exif-rgb-max1024-jpeg90`(등록 버전으로 실행하면 그 버전), `gold_run_id`, `gold_updated_at`
- `BLANK`·`BAD_IMAGE`·`READ_ERROR`·`SHA_MISMATCH`는 모델을 부르지 않으므로 **요청 로그와 비용이 없습니다.**

### 4.4 상태가 바뀌는 경우

```
READ_ERROR ─┐ 다음 실행에서 파일을 읽으면
SHA_MISMATCH ┴─▶ OK / BLANK / BAD_IMAGE   (같은 행이 바뀜)

BLANK / BAD_IMAGE ─▶ 그대로 유지 (같은 sha256은 다시 보내지 않음)
      └ 사진이 교체되면 sha256이 달라져 새 사진으로 새 행이 생김. 옛 행은 남음
```

| 상황 | 결과 |
|---|---|
| 공고의 사진 **주소가 바뀜** | 다시 받아 sha256이 달라짐 → 새로 임베딩 |
| **주소는 그대로, 서버 파일만 바뀜** | 다시 받지 않음 → 다시 시도하지 않음 |
| 빈 사진 기준(4.0)이나 이미지 라이브러리를 바꿈 | 자동으로 다시 시도하지 않음 → 기록을 사람이 정리 |

깨진 파일은 사진 수집 단계에서 먼저 거르고 다시 받으므로 `BAD_IMAGE`는 드뭅니다. 다만 메모리 부족 같은 일시 오류도 `BAD_IMAGE`로 남을 수 있어, **생기면 `last_error`를 확인**합니다.

### 4.5 모델 호출이 실패하면

`BAD_IMAGE`는 **사진 파일**의 문제이고, 여기는 **모델 호출**의 문제입니다.

| | 지금 운영 코드 | #79 적용 뒤 |
|---|---|---|
| 호출 1번 안에서 | 최대 5번 재시도 (408·429·5xx) | 같음 |
| 그래도 실패 | 실행 중단 | 나머지를 계속 보내고, 실패한 사진만 끝에 1장씩 **한 번 더** |
| 또 실패 | - | `API_ERROR`로 남기고 다음 실행에서 다시 보냄 |
| 대기 중이던 호출 | **실행되고도 결과·비용이 기록되지 않음** (가짜 환경에서 재현) | 멈출 때 **취소** (보내지 않음) |
| 키·계정 오류(401·402·403) | 실행 중단 | 바로 멈춤 |
| 5번 연속 실패 (장애) | - | 멈춤 |
| 실패한 호출의 요청 로그 | 남지 않음 | `status = ERROR`, `error_code` |
| Airflow | 10분 뒤 task를 1번 다시 실행 | 멈췄거나 하나도 성공하지 못했을 때만 다시 실행. 몇 장만 실패하면 적재까지 진행 |

벡터 차원이 768이 아니면 두 경우 모두 실행을 중단합니다.

### 4.6 실행 전체의 결과 (Airflow)

| 종료 코드 | 명령 | 뜻 | 이후 |
|---|---|---|---|
| 0 | 모두 | 정상 (사진 몇 장의 `READ_ERROR`는 정상으로 봄) | 다음 단계 |
| 2 | `load` | RDS에 쓸 행이 상한(5,000)을 넘거나 벡터가 이상 | 쓰지 않음 |
| 3 | `canary` | 고정 사진 6장 중 하나라도 유사도 0.99 미만 | **임베딩·적재 중단** |
| 4 | `embed` | 20장 이상이면서 절반 넘게 못 읽음 | 적재 중단 (받은 결과는 저장) |
| 5 (#79) | `embed` | 모델 호출을 멈췄거나 하나도 성공하지 못함 | 적재 중단, Airflow가 다시 실행해 남은 사진만 보냄 |

같은 파일을 3번 이상 연속으로 못 읽으면 로그에 `!!` 경고가 나옵니다.

### 4.7 글 임베딩 (A2) [코드]

| 로그 | `status` | 언제 |
|---|---|---|
| 처리 로그 | `OK` | 카드 벡터를 저장함. `task = text_embedding`, `subject_key = 공고번호`, `input_hash = 카드 해시` |
| 요청 로그 | `OK` | 호출과 벡터가 정상. 여러 카드를 묶으면 `subject_key`는 첫 공고, `batch_size`는 카드 수 |
| 요청 로그 | `ERROR` (`error_code = INVALID_VECTORS`) | 벡터 수·차원·값이 이상. 처리 로그는 남기지 않고 실행 중단 |

호출 자체가 실패하면 두 로그 모두 남지 않고, 다음 실행에서 다시 보냅니다.

### 4.8 canary

| 남는 곳 | 내용 |
|---|---|
| `gold_embedding_canary` | `passed`(통과 여부), `min_cosine`, `threshold`(0.99), 사진별 유사도. 통과·실패 모두 1행 |
| 요청 로그 | 6행, `status = OK`, `task = image_embedding`, `gold_run_id`가 `canary-`로 시작 |
| 처리 로그 | 남기지 않음 |

벡터 차원이 다르면 유사도를 계산하기 전에 오류로 멈추고 Gold에는 남지 않습니다.

### 4.9 태깅과의 구분

| | 태깅 | 사진 임베딩 |
|---|---|---|
| 완료 | `OK` | `OK` |
| 처리했지만 결과 없음 | `NO_RESULT` | - |
| 입력이 없거나 쓸 수 없어 호출 안 함 | `NO_PHOTO`, `NO_TEXT`, `BAD_IMAGE` | `BLANK`, `BAD_IMAGE` |
| 다시 시도하는 실패 | **`FAILED`** (모델 호출·답 형식 오류, 총 3번까지), `READ_ERROR`, `SHA_MISMATCH` (매번) | `READ_ERROR`, `SHA_MISMATCH`, `API_ERROR` (횟수 제한 없음) |
| 요청 로그 | `OK`, `ERROR`, `BAD_ANSWER` | `OK` (#79부터 `ERROR`도) |

- **왜 이름을 바꿨나:** 임베딩도 열리지 않는 사진에 `FAILED`를 썼지만 **다시 시도하지 않는 상태**였습니다. 태깅의 `FAILED`는 **다시 시도하는 상태**라, 공용 로그에서 섞이지 않게 `BAD_IMAGE`로 나눴습니다.
- 사진 태깅도 #78부터 사진 입력 문제에 **임베딩과 같은 값**(`READ_ERROR`·`SHA_MISMATCH`·`BAD_IMAGE`)을 씁니다. `FAILED`는 모델 호출·답 형식 실패만 뜻합니다.
- **적용 상태:** #73이 병합됐고 이미지 빌드도 끝나, **다음 03:00 실행부터 `BAD_IMAGE`** 를 씁니다. 지금까지 해당 사진은 0건입니다.

### 4.10 확인용 조회

```sql
-- 작업별 처리 상태 (공용 로그는 task를 반드시 함께 본다)
SELECT task, status, count(*) FROM rebom_gold.gold_inference_log_test GROUP BY 1, 2 ORDER BY 1, 2;

-- 임베딩에서 확인이 필요한 사진 (prod, 통합 전)
SELECT subject_key, status, attempts, last_error, detail, gold_updated_at
FROM rebom_gold.gold_embedding_inference_log
WHERE status NOT IN ('OK', 'BLANK');

-- 작업별 비용 (한국 날짜)
SELECT date(requested_at AT TIME ZONE 'Asia/Seoul') AS day_kst,
       CASE WHEN gold_run_id LIKE 'canary-%' THEN 'canary' ELSE task END AS job,
       count(*) AS requests, sum(cost_usd) AS usd
FROM rebom_gold.gold_model_request_log_test
GROUP BY 1, 2 ORDER BY 1, 2;
```

### 4.11 상태별 조치

| 보이면 | 할 일 |
|---|---|
| `READ_ERROR`가 3번 이상 | Bronze에 파일이 있는지 확인, 없으면 사진을 다시 수집 |
| `READ_ERROR`가 한꺼번에 많음 | S3 권한·네트워크 확인 |
| `SHA_MISMATCH` | Bronze 파일과 manifest가 어긋났는지 확인 |
| `API_ERROR`가 3번 이상 | `error` 코드 확인 (402면 크레딧, 400이면 사진 확인) |
| `BAD_IMAGE` | `last_error` 확인. 일시 오류면 해당 처리 로그를 사람이 정리한 뒤 다시 실행 |
| `BLANK`가 갑자기 늘어남 | 대체 이미지가 들어오는지 사진을 직접 확인 |
| canary 실패 | task를 다시 실행 → 제공자 비교 → 실제 변경이면 재임베딩 검토. 확인 전 '성공' 처리 금지 |
