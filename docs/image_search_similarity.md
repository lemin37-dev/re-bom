# 사진 유사도 검색: 공고 추천 순위 정하는 방법

작성: 2026-11-20 · 대상: 검색 API, 화면, 임베딩 · 상태: **규칙 확정(11-19), 검색 API 연결은 예정**

> **한 줄 요약**
> 공고의 사진 칸(1~8번)을 **모두** 질의 사진과 비교하고, 그중 **가장 높은 유사도를 그 공고의 점수**로 씁니다.
> 공고는 결과에 한 번만 나오고, 가장 닮은 사진 칸(`best_slot`)을 함께 돌려줍니다. 기본으로 **보호중 공고만** 찾습니다.

---

## 1. 벡터는 어떻게 저장되어 있나

- 사진 **칸 1개 = 벡터 1개**입니다. 첫 사진만 저장하지 않습니다.
- RDS 테이블 `image_embedding`, 키 (`desertion_no`, `image_slot`, `model`), 768차원, 코사인 HNSW 인덱스.
- 예: 사진이 2장인 공고 → 1번 칸 벡터, 2번 칸 벡터 2행.
- 사진이 교체되면(v01 → v02) 같은 칸 행을 새 벡터로 덮어씁니다. 그래서 칸마다 항상 최신 사진 하나만 있습니다.

## 2. 계산 순서

```
질의 사진
 → 저장할 때와 같은 전처리(JPEG, 긴 변 1024) → gemini-embedding-2 768 벡터
 → ① 사진 칸 기준으로 가까운 것 200개 (HNSW)
 → ② 보호중이 아닌 공고 제외
 → ③ 공고별로 묶어 가장 높은 유사도만 남김 (= 공고 점수, 그 칸 = best_slot)
 → ④ 점수 높은 순 정렬 → 상위 k개 공고
```

- 같은 점수면 앞 칸을 대표로 씁니다.
- ①에서 200개를 넉넉히 뽑는 이유: 한 공고가 여러 칸을 차지하고, ②에서 종료 공고가 빠지기 때문입니다. 종료 공고 비율을 보고 조정합니다.

## 3. 예시

질의 사진과 각 칸의 유사도:

| 공고 | 칸별 유사도 | 공고 점수 (최고) | best_slot | 순위 |
|---|---|---|---|---|
| D (종료 공고) | 1번 0.99 | — | — | 제외 |
| C | 1번 0.95, 3번 0.10 (흰 대체 사진) | **0.95** | 1 | 1 |
| A | 1번 0.88, 2번 0.91 | **0.91** | 2 | 2 |
| B | 1번 0.90 | **0.90** | 1 | 3 |

- C는 흰 대체 사진(0.10)이 섞여 있어도 점수가 깎이지 않습니다.
- A는 1번 사진보다 2번 사진이 더 닮아서 2번으로 찾았습니다. 첫 사진만 썼다면 B보다 아래(0.88)였습니다.

## 4. 왜 "가장 높은 사진"인가

| 방법 | 동작 | 판단 |
|---|---|---|
| **가장 높은 사진** | 모든 칸 중 최고 유사도 | **채택.** 어느 칸이든 닮은 사진이 하나 있으면 찾고, 공고마다 한 번만 나옴 |
| 첫 사진만 | 1번 칸만 비교 | 1번 사진이 흐리거나 각도가 다르면 놓침. 나머지 사진을 저장한 의미가 줄어듦 |
| 평균 | 칸들의 평균 | 흰 대체 사진처럼 **관계없는 사진이 섞이면 점수가 깎임** (실제 데이터에서 확인) |

- 로컬 검색 시험에서 같은 공고의 사진끼리는 보통 유사도 **0.9 이상**이었습니다. 그래서 최고값을 써도 다른 칸과 크게 어긋나지 않습니다.
- 사진 칸 결과를 묶지 않고 그대로 보여 주면, 비슷한 사진을 여러 장 올린 공고 하나가 상위를 다 차지합니다. 묶어서 막습니다.

## 5. 보호중 공고만 찾는 이유

- 입양·반환 등으로 **종료된 공고의 벡터도 RDS에서 지우지 않습니다** (11-19 확정).
- 종료 뒤 보호중으로 **복귀하는 공고**가 있기 때문입니다(관찰 4건). 복귀하면 다시 만들 필요 없이 바로 검색에 나옵니다.
- 그래서 검색이 기본으로 `processState = '보호중'`인 공고 안에서만 찾아야 합니다. 공고 상태는 서비스(공고) 테이블에서 읽습니다.

## 6. 글 검색과 합칠 때

- 글 질의와 사진 질의 결과는 **순위**로 합칩니다: `w글/(60 + 글 순위) + w사진/(60 + 사진 순위)`.
- 이때 **사진 순위 = 위 방식(공고별 최고 유사도)으로 정한 순위**입니다.
- 가중치 기본 0.6 : 0.4. "특징 중심" 0.7 : 0.3, "생김새 중심" 0.4 : 0.6.
- 응답이 늦으면(5초 + 2번 재시도 실패) 필터 검색(SQL) 결과만 보여 줍니다.

## 7. 코드

`src/rebom/embedding/store.py`

| 함수 | 하는 일 |
|---|---|
| `nearest(conn, model, vector, k)` | 사진 칸 단위 가까운 순서 (점검용) |
| `best_per_notice(hits, k, keep)` | 칸 결과를 공고별 최고 유사도로 묶음. `keep`으로 보호중 공고만 남김 |
| `nearest_notices(conn, model, vector, k, keep)` | 사진 질의 → `(공고번호, best_slot, 유사도)` 목록. 칸 200개를 뽑아 묶음 |

SQL로 옮기면 이런 모양입니다 (서비스 테이블 이름은 검색 API에서 정함):

```sql
WITH hits AS (
  SELECT desertion_no, image_slot, 1 - (embedding <=> :q) AS sim
  FROM image_embedding WHERE model = 'gemini-embedding-2'
  ORDER BY embedding <=> :q LIMIT 200
), best AS (
  SELECT DISTINCT ON (desertion_no) desertion_no, image_slot AS best_slot, sim
  FROM hits JOIN <공고 서비스 테이블> USING (desertion_no)
  WHERE process_state = '보호중'
  ORDER BY desertion_no, sim DESC, image_slot
)
SELECT * FROM best ORDER BY sim DESC LIMIT :k;
```

## 8. 아직 정할 것

| 항목 | 담당 | 내용 |
|---|---|---|
| 썸네일 | 화면 | 1번 사진으로 둘지 `best_slot` 사진으로 둘지. 점수를 낸 사진과 썸네일이 다를 수 있음. `best_slot`을 쓰면 "왜 이 공고가 나왔는지"가 바로 보임 |
| 공고 상태 연결 | 검색 API | RDS 공고 서비스 테이블과 조인 방법 |
| 후보 수 200 | 검색 API | 종료 공고 비율·결과 수를 보고 조정 |
| 사진 칸만 빠진 경우 | 임베딩·정제 | 보호중 공고에서 API 사진 칸이 사라지면 옛 벡터가 남음. Silver 사진 현재 표가 운영되면 그 기준으로 정리 |
